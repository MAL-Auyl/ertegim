## Problem Statement

The Sept 10 demo (per the prior design doc) ships a fixed two-hero script (fox=counting, owl=rhyming) with a Wizard-of-Oz answer-classification step. Since that doc was written, the WoZ step has already been replaced by a real LLM classifier (Groq chat, openai/gpt-oss-20b) that judges correct/incorrect/unclear against a text criterion, and the berry count / rhyme word are now randomized per session. But the story CONTENT is still a fixed script — the product's own claimed differentiator ("not a branching tree, the answer is processed anew every time") is only half-true: the *judgment* is real AI, the *questions* are not. Beyond the demo, there's also no theme variety (only fox/owl exist; bear has a cover image and nothing else) and no emotional hook beyond a single counting/rhyming game — the narrative mechanics the builder already wrote into IDEA.md (hero needs help, hero is scared, timer, cross-session memory) exist only as prose, not code.

## What Makes This Cool

A hero who actually remembers the child between sessions — "спасибо, что не бросил меня в пещере" / "помнишь, как мы искали брата?" — turns a counting exercise into a relationship. Combined with the second-opinion subagent's find during this session: fold that memory feature together with the design doc's already-deferred "live competency map" into one artifact — not a parent-facing stats dashboard, but a "hero's memory book" the character appears to have written about the child. Same underlying data (what the child practiced, how they did), completely different frame.

## Constraints

- Builder mode, solo, for-fun/hackathon-adjacent project — no stated headcount beyond the user (carried forward from the prior doc).
- No git remote configured — this doc's repo copy is the shareable artifact; there's no PR/CI pipeline to hand this off to yet.
- Real background art for new heroes does not exist and is out of this agent's ability to generate (raster illustration, not code) — confirmed by checking `app/public/images/`: bear has a promo cover only (`cover-bear.png` / `cover-bear-fullbody.png`, no in-story background or rig); rabbit has no art at all.
- Kazakh child-speech STT reliability is still unverified beyond the specific test phrases already tried live in this session ("үш", a rhyme answer) — not a rehearsed range of real child voices.

## Premises

Agreed this session:
1. Plan all three initiatives (theme library, real story agent, narrative mechanics) as one coherent architecture, but sequence them — not build in one week.
2. The real story agent (LLM actually generating question/line content, not just classifying a fixed script) is the highest-leverage of the three: it's the literal claimed product differentiator and doesn't exist in code yet.
3. New background art for the theme library is a hard blocker not solvable by code alone — needs either sourced art or a deliberately accepted placeholder.
4. Narrative mechanics (need-help framing, fear-reversal, timer, cross-session memory) is independent of the other two and can be prototyped directly on the existing fox/owl script.

## Approaches Considered

### Approach A: Narrative-first (minimal viable)
Ship fear/need-help/timer/memory on the current fox/owl script now — zero new art, zero new AI-reliability risk. Real story agent and theme library come after.
- Effort: S-M (human: ~4-5 days / CC: ~4-6 hours across sessions) — revised up from an initial ~2-3 day / ~1-2 hour estimate: rewriting narration for two heroes, designing the (currently undesigned) memory-book content model, localStorage session logic, and a `reportPanel` rebuild are four separate nontrivial pieces, not one. This estimate already includes the Approach-C-style `reportPanel` rebuild as one of the four pieces — it is not extra work on top.
- Risk: Low
- Pros: No blockers right now; matches the builder's own demonstrated motivation (the emotional lines were written before any code); reuses `story.js`'s existing STORY object and the classify pipeline's existing per-question data.
- Cons: Doesn't touch the actual claimed differentiator (real story agent) for a while; theme library stays blocked on art with no forcing function to resolve it.

### Approach B: Story-agent-first (ideal architecture)
Build the real story agent first (e.g. via Outlines/constrained decoding on the existing Groq account), so narrative variety and new themes generate cheaply once it exists, instead of being hand-scripted per hero.
- Effort: XL (human: ~2-3 weeks / CC: several days of iteration — this is a genuinely hard reliability problem, not a size problem)
- Risk: High — stacks two unverified reliability risks (Kazakh child STT + live generation staying in-grammar and age-appropriate) before shipping anything visible.
- Pros: Actually delivers on the core differentiator claim; once built, both narrative variety and new themes become generation, not hand-authoring.
- Cons: Highest effort and risk of the three; first visible progress is delayed the longest — a classic "boil the ocean first" trap for a solo builder without a deadline forcing scope discipline.

### Approach C: "Memory book" (creative/lateral — from the cross-model second opinion)
Fuse cross-session memory with the deferred "competency map" into one screen: replace the current static `reportPanel` mock (`app/public/index.html`) with an in-character memory-book screen built from the classify results already being computed per question, plus localStorage for cross-session recall.
- Effort: S-M (human: ~1-2 days / CC: ~2 hours) — narrower scope than a full Approach A build
- Risk: Low
- Pros: Turns two currently-separate future features (memory + competency map) into one shipped artifact; strongest emotional payoff per the builder's own writing; doesn't require solving Approach B's hard AI-reliability problem.
- Cons: Alone, it's still content/UI layered on the same fixed fox/owl script — doesn't move the "is this really AI-driven" claim; scope can quietly grow deciding what a memory-book page looks like for every combination of session outcomes.

## Recommended Approach

**A, incorporating C as the format for its memory feature** (user-selected this session): build narrative mechanics on the current script, and specifically implement the "remembers the child" piece as the memory-book reframing of the parent-report screen rather than a second, separate feature. This is the only path with zero blockers today, and it directly matches the emotional core the builder had already written before any of this was designed. Combined effort: same as Approach A above (~4-5 days / ~4-6 hours CC) — C is not a separate approach built alongside A, it's the specific design for one of A's four pieces (the `reportPanel` rebuild), so there is nothing to add on top.

Approach B (real story agent) is not rejected — it remains the acknowledged highest-leverage item (Premise 2) — it's sequenced second, once there's runway to absorb its risk without a stage deadline forcing corner-cutting.

## Open Questions

- Exact memory-book content model: what does a "page" look like for each combination of session outcomes (correct-first-try vs. re-asked vs. auto-revealed, per hero)? Memory is scoped **per hero** (fox and owl keep separate history — the example callback lines are story-specific, e.g. the brother-search line belongs to one hero's arc, not a shared pool). Not designed this session — first thing to sketch when Approach A/C build starts (Next Steps #1).
- Multi-child-per-device (siblings sharing the same browser) is explicitly **out of scope for v1** — localStorage is keyed to the device, not a child identity, so two children on one device will see each other's callback lines. Acceptable for a demo/single-child use case; flag as a known gap, not a bug, if raised.
- Timer mechanic: decided as **optional/non-blocking** for v1 (Success Criteria excludes it from the "done" bar) — not decided as forbidden; it can still land in the same pass if time allows, it's just not required to call Approach A complete.
- Theme library (bear/rabbit) art sourcing is unresolved — no decision this session on whether the builder will source it, or whether a placeholder is accepted.
- Real story agent (Approach B) timing is not scheduled — "second, when there's runway" is directional, not a date.

## Success Criteria

Narrative mechanics (Approach A) ship as: the current fox/owl script's framing changes from generic "let's play" to a needs-help/fear-reversal hook, a session-end memory-book screen replaces the static `reportPanel` mock with content built from real per-question classify results plus a per-hero cross-session callback line (conditioned on the content model from Next Steps #1 existing first — this is not a given, it's the first build task), and this all runs on the existing STT/classify/TTS pipeline with no new external dependency or reliability risk introduced. Concretely: no new npm/package dependency added, no new network call added beyond the existing `/api/transcribe`, `/api/classify`, `/api/speak` endpoints, no child voice/name capture added (see Next Steps #3). **The timer mechanic is explicitly out of the v1 "done" bar** — Approach A ships without it; it's a later addition if time allows, not a blocker to calling this done.

## Next Steps

1. Sketch the memory-book content model (Open Questions #1) — what data already computed by `/api/classify` maps to what in-character text, for fox and owl, scoped per hero. Before finalizing the effort estimate above, enumerate the actual number of outcome combinations this needs to cover (heroes × correct-first-try/re-asked/auto-revealed × has-prior-session-or-not) — hand-authoring text for each combination is likely the single largest unknown in this plan, bigger than the other three pieces. Also define what counts as a "completed" session eligible for a future callback line (e.g., reached the ending state vs. abandoned after 1 of N questions) so an abandoned session doesn't produce a misleading callback next time. **Blocks step 4** — the screen can't be built until this model exists.
2. Rewrite `story.js` narration lines (intro/reveal beats) around the need-help/fear framing — text-only change, no new code paths.
3. Add localStorage-backed session memory — session count and last outcome **per hero** (fox and owl tracked separately, not a single device-wide value), no child name/voice capture (deliberately excluded, see Success Criteria: capturing a name either requires STT, reintroducing the exact unverified-reliability risk Approach A was chosen to avoid, or a parent-typed field, which is new UI scope not covered by this doc). A callback line renders at the start of the next session for a given hero where localStorage has prior data for that hero — "next session" means the next time `index.html` loads with existing localStorage state, not a time-boxed window. If localStorage is unavailable, cleared, or the read fails for any reason (private browsing, quota, different browser), fall back silently to the current first-time intro with no callback — same behavior as the empty-state case, never an error shown to the child.
4. Replace the static `reportPanel` markup in `app/public/index.html` with the memory-book format. **Correction from an earlier draft of this doc:** `app.js` does not currently retain classify results across questions in a structured, reusable form — today's UI only shows the latest transcript/verdict transiently (see `classifyAndSuggest()` in `app/public/app.js`). This step therefore includes adding a small client-side array that accumulates `{hero, questionId, label, reason}` per answered question during the live session, which the memory-book screen then reads at session end. This is new client-side state, not a reuse of something that already exists — still no new backend endpoint or dependency required.
5. (Secondary, time-permitting) add the sunrise/timer framing as a visible countdown element.
6. Once narrative mechanics ship and there's runway: revisit Approach B (real story agent) as its own office-hours session — it deserves its own premise challenge and alternatives pass given its size and risk, not a subsection of this one.
7. Theme library (bear/rabbit) stays blocked until an explicit decision on art sourcing vs. placeholder — flag to the builder before starting any work on it.

## Reviewer Concerns

Persisted after 3 rounds of adversarial review (final score 8/10) — not blocking, addressable when the corresponding Next Steps item is actually implemented:

1. **Per-hero session count moves in lockstep, not independently.** `story.js`'s STORY object is one linear state machine — every playthrough runs fox then owl in a single pass, so per-hero *session count* will always be numerically identical between the two heroes; only per-hero *last outcome* (correct/re-asked/revealed) actually diverges. Note this explicitly before starting Next Steps #1's content-model work so a future implementer doesn't build separate counters expecting them to diverge.
2. **Classify-results accumulator lifecycle unspecified.** Next Steps #4's new `{hero, questionId, label, reason}` array needs a stated reset point and persistence scope: initialize it empty at `renderState(START_STATE)`, keep it in-memory only (not persisted) — a page reload should discard an in-progress session's classify history, so a stale/abandoned attempt can't leak into a later "completed" session's memory-book.
