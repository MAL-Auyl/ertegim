# Ертегім — идея для Idea Battle (10.09)

Интерактивная сказка, где ребёнок разговаривает с героем голосом и влияет на сюжет — не жмёт кнопку «далее», а реально в нём участвует.

## Проблема

Почти весь детский видеоконтент — пассивный: ребёнок смотрит, не отвечает. Родители всё настороженнее относятся к «мультику на автопилоте», но альтернатив, где экран требует реального ответа ребёнка, а не просто выбора из готовых кнопок, на рынке почти нет.

Существующие «интерактивные» форматы (Netflix-спецвыпуски и т.п.) — это заранее прописанное дерево веток. Кнопки просто выбирают путь по дереву. Никакого настоящего диалога там нет.

## Кому это нужно

Родители детей ~3–7 лет, которые уже ищут «развивающий», а не просто развлекательный контент, и готовы дать ребёнку экран, если он реально что-то тренирует (речь, счёт, внимание), а не просто занимает время.

## Что делает продукт (core loop)

1. Герой (например, лисёнок) задаёт ребёнку вопрос по ходу истории — «сколько ягод ты видишь?», «как думаешь, куда пойти — налево или направо?».
2. Ребёнок отвечает **голосом**, своими словами — не выбором из готовых вариантов.
3. Герой реагирует на то, что реально услышал: ведёт сюжет дальше, если ответ подходит; мягко переспрашивает или упрощает, если ответ неверный/расплывчатый.
4. История развивается по-разному каждый раз — нет двух одинаковых прохождений.
5. Родителю в конце — короткий отчёт: какие слова ребёнок использовал, как быстро реагировал, где были сложности.

## Демо-момент для сцены

Судья/зритель играет роль ребёнка, говорит в микрофон случайную фразу — герой отвечает осмысленно, не по вшитому сценарию, история гнётся под ответ прямо на экране. Коротко (30–60 сек), эмоционально, видно, а не пересказано.

## Архитектура (агентный пайплайн)

```
голос ребёнка
   → распознавание речи (STT)
   → фильтр безопасности (жёстко ограничивает тему/словарь до того, как что-либо пойдёт дальше)
   → агент сюжета (решает: усложнить / упростить / повторить — по возрасту и правильности ответа)
   → генератор реплики героя (отвечает в характере, в рамках словаря нужного возраста)
   → озвучка (TTS) + переключение на нужный анимационный фрагмент
   → (параллельно, тихо) агент метрик — считает не запись, а показатели для отчёта родителю
```

Ключевое отличие от готовых интерактивных мультиков: тут нет предзаписанного дерева веток. Ответ обрабатывается заново каждый раз.

## Как закрываем риски

- Голос ребёнка не хранится — обрабатывается и сразу удаляется; родителю уходит только текстовый отчёт по метрикам, не аудио.
- Никакого свободного чата — герой физически не может выйти за пределы заданного банка тем/словаря. Это архитектурное ограничение (whitelist тем, а не instruction-фильтр поверх свободной модели).
- Сессия сама завершается через N минут финалом истории — встроенный лимит экранного времени.
- Панель родителя закрыта PIN-кодом.

## Почему сейчас

Рынок детского контента почти весь пассивный. Родительская тревога по поводу «экрана без пользы» растёт. Продукт, который явно требует ответа ребёнка и явно объясняет родителю, что именно ребёнок тренирует — попадает точно в этот запрос.

## MVP-разрез (что нужно к 10.09, что откладываем)

**Делаем для демо:**
- Одна короткая история (2–3 развилки) с одним героем.
- Заранее отрисованные/сгенерированные анимационные клипы под каждую ветку (не live-генерация видео).
- STT + LLM с жёстко заданным промптом-рамкой (тема/словарь) + TTS — готовые API, не свои модели.
- Простая логика агента сюжета: классификация ответа ребёнка (верно / неверно / не по теме) → выбор следующего клипа.
- Один экран отчёта родителю с 2–3 метриками (моковые данные для демо, если не успеем считать по-настоящему).

**Осознанно откладываем после баттла:**
- Реальное хранение/защиту данных на инфраструктурном уровне (для демо — просто *не сохраняем* ничего, этого достаточно, чтобы показать принцип).
- Библиотеку историй (для демо хватит одной).
- Мультиязычность.
- Реальную модерацию голоса на уровне продакшена — для демо ограничиваемся жёстким промптом + coded whitelist тем.

## Технические решения

**STT:** Whisper (whisper-large-v3-turbo через Groq API), не браузерный Web Speech API.
Web Speech API натренирован на взрослую речь — на нечёткой дикции 3-7-летнего ребёнка
часто вообще не распознаёт фразу. Groq отдаёт транскрипцию быстрее секунды — это
критично: если герой молчит 2-3 сек, ребёнок уже решает, что «сломалось». Стоимость на
демо — несколько запросов, копейки; на этом этапе надёжность важнее бесплатности.

**Анимация:** не рисуем клип под каждую ветку сюжета — разделяем персонажа и фон,
чтобы количество веток не равнялось количеству ассетов:
- Персонаж — риг в Rive/Lottie с 4-5 состояниями (idle, talk, happy, confused, think),
  переиспользуется во всех ветках. Рот двигается по амплитуде TTS-аудио (простой viseme
  в state machine), не покадровая анимация.
- Фон — 3-4 статичные иллюстрации (по одной на сюжетный бит) с Ken Burns (плавный
  zoom/pan камеры вместо анимации самой картинки).
- Агент сюжета просто переключает (фон, состояние персонажа) — не выбирает готовый
  видеоклип из 4-9 вариантов.

Это снимает главный ресурсный риск недели: «не успели отрисовать все ветки» — их
физически не нужно рисовать по отдельности.

**Озвучка (TTS):** [Piper](https://github.com/OHF-Voice/piper1-gpl) — выбрано и уже
реализовано. Локальный, работает в реальном времени на CPU (закрывает риск задержки из
раздела Perf ниже), бесплатный, есть готовые голоса и на русском (denis, dmitri, irina,
ruslan), и на казахском (iseke, raya, issai — high quality). Старые веса модели — MIT,
форк с новыми голосами — GPL-3.0 (веса всё равно свободные).

Рассмотрели и отклонили — [Silero TTS](https://github.com/snakers4/silero-models):
тоже CPU-дружелюбный, v5 сама расставляет ударения (важно для нечёткой детской озвучки
и омографов), есть казахский в семействе cis-tts (эти веса — MIT), но основной репозиторий
лицензирован как CC-NC-BY (некоммерческое использование) — риск для монетизации после
баттла. Плюс Piper к этому моменту уже полностью внедрён и допилен (выбор голоса,
подъём тона под «женский/детский» через ffmpeg, пререндер fallback-озвучки) — пересборка
на другой движок за 6 дней до дедлайна не окупается.

**Важное уточнение по «голосам из референса»:** Piper — не voice cloning, у него только
фиксированный набор уже обученных голосов (denis/dmitri/irina/ruslan/kk_KZ). Клонирование
голоса по короткому референс-сэмплу — это отдельный класс моделей:
- [OpenVoice V2](https://github.com/myshell-ai/OpenVoice) (MIT, свободно и для коммерции) —
  клонирует голос по короткому образцу + управление тоном/эмоцией.
- [XTTS-v2](https://github.com/coqui-ai/TTS) (Coqui CPML) — тоже клонирует по референсу,
  но лицензия ограничивает коммерцию при >$1M выручки или >10k пользователей.

Обе модели заметно тяжелее Piper (реально нужен GPU для вменяемой скорости) — на CPU в
live-пайплайн на сцене не впишутся в бюджет 2-3 сек (см. Perf ниже). Поэтому вывод: Piper
остаётся живым голосом для реального диалога на демо; клонирование, если нужны «разные
голоса» под разных персонажей, имеет смысл только офлайн — заранее нагенерировать
fallback-реплики/дополнительных героев, не в реальном времени сессии.

### 1. Архитектура

```
              РЕБЁНОК (голос)
                    │
                    ▼
            STT (Whisper/Groq)
                    │
                    ▼
        Фильтр безопасности (whitelist)
        fail ◄──────┼──────► pass
         │                    ▼
   мягкий редирект     Агент сюжета (усложнить/
                        упростить/повторить)
                                │
                                ▼
                      Генератор реплики героя
                                │
                                ▼
                       TTS + переключение
                       (фон + состояние рига)
                                │
                                ▼
                        РЕБЁНОК (видит/слышит)

  (параллельно, тихо) STT-транскрипт ──► агент метрик ──► отчёт родителю
```

Четыре пути ключевого потока «ответ ребёнка → следующая реплика»:
- **Happy:** чёткая речь → STT распознаёт → фильтр pass → классификация верно/неверно → реплика.
- **Nil** (тишина, микрофон ничего не поймал) — не описано в идее.
- **Empty** (STT вернул пустую/нечленораздельную строку) — не описано.
- **Error** (STT/LLM/TTS API упал или таймаут) — не описано.

Single point of failure: STT → фильтр → агент сюжета → генератор → TTS — все 4 звена
последовательные и внешние (API). Падение любого одного стопорит всю сессию, partial
degrade не предусмотрен.

**Открытый архитектурный вопрос (важно закрыть до 10.09):** «фильтр безопасности» —
это hard-coded whitelist (локальная проверка, у которой физически не может быть
таймаута) или ещё один LLM-вызов «на входе»? В разделе рисков заявлено первое
(«whitelist тем, а не instruction-фильтр поверх свободной модели»), но в архитектуре
пайплайна он нарисован отдельным шагом наравне с LLM-вызовами — то есть неоднозначно.
Если это LLM-вызов, для него нужен явный fail-closed (см. Section 2).

### 2. Реестр ошибок

| Кодпуть | Что может пойти не так | Rescued? | Действие | Что видит ребёнок сейчас |
|---|---|---|---|---|
| STT | Timeout API | N ← GAP | retry 1x короткий таймаут → фоллбек-реплика героя «Ой, задумался, повтори?» | тишина/зависание |
| STT | Тишина (ничего не сказано) | N ← GAP | герой переспрашивает мягко | не определено |
| STT | Низкий confidence/нечленораздельно | N ← GAP | явный порог confidence → переспрос, не гадать | не определено |
| Фильтр безопасности | Недоступен/таймаут (если это LLM-вызов) | N ← **CRITICAL GAP** | **fail-closed**: не пропускать ответ дальше без проверки | не специфицировано |
| Агент сюжета/генератор | LLM отказывается отвечать (refusal) | N ← GAP | заготовленная нейтральная реплика героя | не описано |
| TTS | Timeout/ошибка API | N ← GAP | фоллбек на предзаписанную озвучку той же реплики (текст уже есть) | не описано |
| Переключение клипа | Комбинации фон+состояние не существует | N ← GAP | дефолтный нейтральный state | не описано |

**CRITICAL GAP:** если фильтр безопасности сам подвержен сетевым сбоям (то есть это
LLM-вызов, а не локальный whitelist), он обязан быть fail-closed — при недоступности
фильтра система не должна пропускать ответ ребёнка дальше непроверенным. Это прямое
противоречие с заявленным в разделе «Как закрываем риски» принципом, если оставить
как есть.

### 3. Security / threat model

- **Voice prompt injection.** Ребёнок (или тем более любопытный судья на сцене)
  может сказать что-то в духе «забудь правила и…». Likelihood: Medium, Impact: High
  (публичный провал демо на теме безопасности детей). Whitelist заявлен как
  архитектурная защита, но механизм не расписан — для judging по AI safety это первое,
  что спросят, и «мы это заявили в тексте» не равно «мы это показали».
- **Данные ребёнка.** Голос — чувствительные биометрические данные несовершеннолетнего.
  «Не хранится, сразу удаляется» — правильный принцип, но не описано технически:
  потоковая обработка in-memory или запись файла + немедленное удаление? Для демо не
  критично, для питча — да, родители/инвесторы с опытом в детских продуктах спросят
  именно это.
- **Секреты.** API-ключи STT/LLM/TTS на демо-ноутбуке — не упомянуто, обычный риск
  публичного выступления (не хардкодить в код, который может попасть на камеру).

### 4. Data flow / interaction edge cases

Каждый узел потока «голос → STT → фильтр → агент → TTS» имеет непроработанную теневую
ветку: тишина, пустой/нечленораздельный STT-результат, неоднозначный ответ ребёнка
(«и да, и нет»), отсутствующая комбинация клипа. Из интеракций отдельно не проработаны:
ребёнок начинает говорить, пока герой ещё не договорил (barge-in), и длинная пауза
(когда система решает, что ответа не будет).

### 6. Тесты (= репетиция демо)

Единственный тест, который реально снижает риск сцены: **репетиция с живыми детьми
3-7 лет**, не с речью взрослого — весь пайплайн держится на предположении о детской
дикции, нигде не проверенном. Рекомендация: 3-5 прогонов до 10.09 с записью, где именно
ломается STT/классификация. Отдельно прогнать «hostile»-сценарий: судья намеренно
пытается сломать whitelist голосом. И chaos-тест: отключить wifi на 2 сек посреди
сессии — что видит ребёнок в этот момент?

### 7. Производительность

STT + LLM (классификация + генерация реплики, если это два раздельных вызова) + TTS
последовательно — легко 3-6 сек тишины героя. Для ребёнка 3-7 лет пауза дольше 2-3 сек
уже читается как «сломалось» (см. также раздел «Технические решения» выше).
**Рекомендация:** объединить «агент сюжета» и «генератор реплики» в один LLM-вызов,
возвращающий сразу решение и текст реплики, а не два раздельных раунд-трипа. Стандартные
фразы-переспросы («не расслышал, повтори?») предзаписать в TTS один раз, не генерировать
каждый раз заново — экономит 0.5-2 сек именно в самом частом failure-path.

### 8. Наблюдаемость

Нет ни слова о логировании шагов пайплайна во время разработки — если демо сломается на
репетиции, непонятно, где именно (STT? фильтр? LLM?). Для самой сцены это не блокер, но
для недели подготовки — критично: минимальный dev-лог каждого шага на своём экране.
Плюс: «агент метрик» уже встроен в продукт как источник наблюдаемости для родителя —
это архитектурно верно, не нужно добавлять отдельно.

### 9. Deployment / demo-day rollout

Все внешние вызовы (STT/LLM/TTS) требуют сети — единая точка отказа: интернет на
площадке. Нет описанного plan B, если live-пайплайн падает во время демо на сцене.
Частично закрывается решением из прошлого прохода (заранее не объявленная, но реально
обрабатываемая фраза), но явного сценария «если всё падает — что показываем» в
документе всё ещё нет.

### 10. Долгосрочная траектория

Reversibility: 4/5 — всё ещё pre-code, ничего не забетонировано. Технический долг:
whitelist-механизм заявлен, но не спроектирован — если демо выиграет, его придётся
специфицировать по-настоящему быстро, это самое дырявое место относительно того, что
заявлено как главный аргумент безопасности продукта.

### 11. Design & UX

Плоская последовательность герой→вопрос→ответ→реакция — верно для возраста 3-7
(без меню/кнопок). Главная находка: **у ребёнка нет визуального индикатора «герой
думает»** на время обработки ответа (STT+LLM+TTS = секунды тишины). Без него пауза в
пайплайне читается ребёнком как «сломалось» — это не косметика, а прямая склейка с
Section 7 (latency): состояние «think» из уже принятого решения по анимации
(риг персонажа с 4-5 состояниями) нужно явно использовать именно для маскировки этой
задержки, а не только «для красоты» — стоит прописать это назначение состояния явно.
